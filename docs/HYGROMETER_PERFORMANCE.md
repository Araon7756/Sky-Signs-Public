## 可重复测试入口

性能测试为独立的 opt-in 模式，默认 `runClientGameTest` 仍执行原有完整回归。仅在隔离开发目录执行：

```sh
export JAVA_HOME=/path/to/jdk-21
export GRADLE_USER_HOME=/path/to/gradle-cache
export SKYSIGNS_PERFORMANCE_TEST=1
export SKYSIGNS_XVFB=/path/to/Xvfb
bash scripts/run-client-tests-xvfb.sh --offline
```

`--offline` 仅适用于缓存完整的环境；新环境先取得既有版本的依赖。脚本不安装 JDK、图形库或模组，不修改玩家实例。已有 `DISPLAY` 时复用显示；否则启动本任务的 Xvfb（禁用 TCP 监听），退出时仅清理本任务的显示进程。默认请求软件渲染；有实际 GPU 的环境需自行明确设置并记录驱动。Windows 或已有显示环境可以直接设置 `SKYSIGNS_PERFORMANCE_TEST=1` 后使用 Wrapper 的 `runClientGameTest`。

输出位于实际测试运行目录：`performance-results/hygrometer-<timestamp>.csv`、`logs/latest.log` 和 `screenshots/*perf-round*`。识别日志中的 `SKYSIGNS_PERF`、`SKYSIGNS_ALGORITHM`、`SKYSIGNS_PERF_OPTIONS`。性能模式替代本次完整回归，不能把它成功写成完整回归通过；取消环境变量后才能运行完整回归。

## 对照场景与测量边界

临时平坦世界内固定晴天，在 Y=200 的不透光平台上创建 16×8 台仪表，固定玩家位置和视角。扫描区域的干燥层完全无水；有水组在扫描顺序的首位置放水。两组都有相同的石质遮挡层，水层不会直接暴露给镜头；底层和边界围住水体。每组验证实际方块；湿度计组额外验证 128 台仪表读数与当前湿度计算一致。

| 场景 | 用途 |
| --- | --- |
| 空平台，镜头朝向平台 | 无仪表基线 |
| 128 台气压计，朝向仪表 | 相似外壳和指针，气压采样不扫描水体 |
| 128 台湿度计，无水，朝向仪表 | 245 次流体查询的最坏扫描路径 |
| 同一湿度计场景，背向仪表 | 保留服务端采样，减少视野内仪表负载；不是精确渲染器计时 |
| 128 台湿度计，有水，朝向仪表 | 每次首次查询即命中水，控制扫描路径长度 |

每场景预热 80 tick、测量 240 tick，重复三轮；第二轮反向运行五个场景。放置、校验和截图位于采样窗口外。世界 tick 计时只覆盖主世界 START/END_WORLD_TICK 事件间隔，不是完整服务器 tick；帧间隔覆盖 WorldRenderEvents.END_MAIN 之间的间隔，包括调度、帧率限制等，不能直接当作 GPU 绘制耗时。P95 没有性能通过阈值断言，断言只保证场景正确、样本足够和未触发 AFK 限帧。

性能模式临时将 AFK 限制改为仅最小化时限制，并关闭垂直同步，在每阶段前后校验限帧原因为 NONE；结束时恢复选项，不保存玩家配置。首次试跑发现原版 AFK 限制把后半段压到约 30 FPS，已终止并排除该批帧数据。不能把此平台误判为湿度算法瓶颈。

另在服务器线程上独立计时水体扫描、完整湿度计算和气压计算。每批调用 128 次，8 批预热、24 批测量；消费结果，防止无用计算被优化掉。通过 MethodHandle 直接调用实际私有水体扫描并验证干／湿结果，无生产埋点。批量数据仅说明热缓存下的计算成本，不能当作 JMH、每 tick 平均成本或实时采样比例；完整湿度计算还包括天气状态与群系访问，不应把两组中位数相减视为精确分解。

### 证据与结论

- **扫描有明确的可优化成本。** 无水时每次遍历 245 个位置；首次命中水时仅查一个。实际扫描批次中位数相差约 33 倍，完整湿度计算相差约 24 倍。测量顺序、MethodHandle 调用与 JIT 使“独立扫描比完整湿度计算略慢”成为可能，不能将这两项相减归因；需要正式微基准时另用适合的工具。
- **本轮帧差异更符合可见仪表负载的影响。** 三轮中，湿度计背向帧中位数均低于朝向；气压计朝向也比空平台慢。有水组将扫描缩短，却没有降低帧中位数。数据支持继续调查可见模型／指针、客户端调度和软件渲染成本；没有精确到单一渲染方法的 CPU／GPU profile，不能宣称某个 renderer 已被定位为唯一瓶颈。
- **世界 tick 未出现明确的水体路径主导恶化。** 三轮中位数受预热／主机波动影响，干／湿组差异方向也不稳定。最坏批量成本可作为缓存设计依据，但本场景仪表错峰采样，不是每 tick 同时做 128 次扫描。
- **beta.7 历史 Windows 帧 P95 上升的根因仍未确定。** 本次环境、渲染方式和测量窗口不同；AFK 限帧只证实污染了本次首次试跑，不证明历史记录也受同一原因影响。缓存不应被描述为已经修复历史帧 P95。

## 缓存设计建议

先把优化目标定义为减少重复流体查询和服务端采样成本；如果实际帧瓶颈来自绘制或环境限帧，水体缓存不能替代相应调查。

1. **仅缓存附近是否有水。** 湿度每次仍读取当前天气、群系气候和海拔，保留目前的秒采样与错峰。仪表、气象站、forecast 在 `AtmosphericReadings` 内共享同一查询入口，避免三个互不一致的缓存。
2. **第一版按精确位置缓存。** key 为服务端 world 实例内的 `BlockPos.asLong()`，不同维度独立；不能直接用区块级一个布尔值，否则区块边缘或不同高度会错误共享结果。区域优化若后续需要，应缓存水体空间信息，再按原始 7×5×7 范围查询。
3. **正负结果都缓存，使用游戏 tick 过期。** 候选有效期为 20／60／100 tick，先测命中率和水体变更延迟再选默认值。不会未经测量承诺 5～10 秒最优。若第一版只有 TTL，必须明确放水、收水、水流、水含方块和命令编辑的最大可见延迟；过期后回到原始扫描，不能把“未监听修改”写成实时失效。
4. **控制生命周期与内存。** 每个 world 设置有界容量，候选上限 4096 条，使用访问顺序淘汰；此数值需结合内存实测调整。区块卸载时失效所有扫描范围与该区块相交的条目（包括距离边界 3 格的邻区位置），世界卸载／服务端停止清理。缓存不持久化，不增加数据版本，不留下跨世界静态强引用。
5. **不因缓存查询额外加载区块。** 实施前核对原始流体查询在边界的加载行为；未加载邻区不得被缓存成确定的“无水”。需要为不完整扫描定义可诊断的短期／不缓存策略，并检验重新加载后的恢复行为。
6. **变更失效分阶段评估。** 即时覆盖放水／收水等事件并不等于覆盖水流、含水方块、命令、结构及其他模组。若引入全量方块修改监听，需证明监听成本低于节省的扫描成本。先采用有界 TTL＋卸载清理，再决定是否值得增加更广的失效机制。

## 缓存实施验收

- 与无缓存参考扫描对照，覆盖范围边界、不同高度、不同维度、无水／源水／流水／含水方块，以及多个观测入口共享同位置的情况。
- 放水、移水、自然流动、天气变化、区块卸载／重载、世界重开；检查声明的最大水体更新延迟与天气即时更新分别成立。
- 固定时刻与天气比较完整湿度百分比；确认缓存没有改变群系模型、气压路径、网络频率或存档数据。
- 记录原始查询次数、命中率、淘汰、缓存占用与实际服务器成本；分别测试集中仪表、分散仪表、反复 forecast 和站报告。冷热缓存分开，多轮对照。
- 复用本基线测量 tick 与帧间隔；若帧数据没有收益，报告实际服务端收益，不宣称解决 beta.7 历史帧 P95 上升。

独立服务端、多人、玩家真实旧世界、长期运行和硬件 GPU 矩阵仍需各自验收，本任务没有覆盖。

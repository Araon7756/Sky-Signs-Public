## Sky Signs 配套光影规划（未来探索）

2026-10-20：维护者确认将配套光影纳入未来规划。目标是让天空、植被、降水与仪表读数共同呈现同一套天气和风况，增强天气观测的现场感。方向已确认，具体设计、实现与验收尚未开展；暂不绑定版本或发布日期，也不作为当前 0.7 阶段的必交付项。

优先在天气阶段与客户端风况接口稳定后，选择合适的现有光影开展小范围适配原型；根据效果、性能和维护成本，再决定是否扩展为独立的 Sky Signs 专用光影包。光影作为可选增强，无光影时保留模组的基础观测与反馈体验。

### 第一阶段：选择基础并验证数据桥接

- [ ] 明确目标 Minecraft／Iris／Sodium 组合，评估光影基础的风格、性能、修改与分发许可；尚未指定 Photon 或其他光影，也未决定从零开发完整渲染方案。
- [ ] 设计从客户端天气／风况状态到光影输入的桥接，明确风向、风强、天气阶段与过渡值的语义、插值和失效回退；具体 Iris 接入方式与接口兼容性需验证，不预先承诺现成的稳定扩展 API。
- [ ] 保持服务端决定天气、风况和仪表读数，客户端光影只负责表现；视觉设置不改变真实天气、仪表数据或其他玩家的设置。

### 第二阶段：验证最小联动原型

- [ ] 植被摆动跟随同一风向与风强；定义风的来向与视觉位移方向的转换，避免植被、雨幕和仪表方向矛盾。
- [ ] 在选定光影中验证降水随风倾斜，覆盖冷群系降雪与屋檐遮挡；现有 Iris 光影启用时停用模组降水倾斜的策略，在目标组合取得验证前继续保留。
- [ ] 在天气逻辑提供相应状态后，验证天气阶段／过渡驱动云层与光照变化；雨前压暗、云层增厚和雨后恢复属于候选效果，不能把光影自身的随机天气当作服务端天气或预报。
- [ ] 使用固定地点、时间与可复现天气条件，对比无光影、原光影和适配原型的晴天／小雨／雷暴画面与帧时间；小雨效果以实际可提供的降水状态为限，不据此承诺独立降雨强度系统。

### 第三阶段：按实机结果决定扩展与交付

- [ ] 评估独立光影包、现有光影适配或与上游合作的交付方式；再决定是否增加雾、湿润感、闪电照明及更复杂的云层，并明确维护范围。
- [ ] 提供适当的视觉强度、闪光和性能选项。模组侧风反馈开关与强度沿用统一设置入口，各玩家独立控制；光影包自身的画质选项按选定方案设计。
- [ ] 在隔离实例与世界副本中记录真实 GPU 的效果和帧时间，覆盖窗口缩放、光影重载／切换、闪电、雪、遮挡、维度切换与长时间天气过渡；历史 Photon 黑屏与规避记录仅作回归线索，不视为已修复或新组合已通过。
- [ ] 按精确源码／光影版本、依赖、显卡与驱动记录通过、失败和未验证项；Cloud 可负责候选实现与自动检查，Local 负责真实渲染、性能与人工画面验收，多人与专服实测仍须另获授权。

本节仅记录规划方向，不授权修改 Java、GLSL、依赖、网络协议或存档结构。每阶段开始前另行确认范围，按独立分支、验证、PR、维护者确认的流程推进；当前没有新增可下载光影或已完成的兼容性承诺。

## 多版本与多加载器支持规划

Sky Signs 的长期支持方向不限于 Minecraft Java 1.21.10，也不限于 Fabric。当前已发布版本和现有工程仍以 **1.21.10 + Fabric** 为支持基线；以下均为待评估、待实施的兼容规划，具体目标版本、加载器、维护周期和发布日期尚未确定。

本方向与功能版本路线并行评估，按用户需求、依赖可用性、维护成本及现有质量问题安排实施，不将所有候选组合一次性纳入发布门槛。

### 第一阶段：选择 Minecraft 版本并完成试点

- [ ] 评估后续 Minecraft Java 版本的升级支持，以及有实际需求的较早版本回移植；逐项核对 Java、映射、加载器、API、资源格式和存档接口差异。
- [ ] 先选定一个额外 Minecraft 版本作为试点，明确支持范围、维护周期和停止维护条件，再决定是否扩大版本矩阵。
- [ ] 在独立分支和隔离世界副本中验证天气／风况、仪表／命令、保存重开与迁移、客户端显示及适用的渲染兼容。跨 Minecraft 版本的世界降级不因模组适配而取得安全保证。

### 第二阶段：评估并试点其他加载器

- [ ] 将 NeoForge、Forge 等列为候选，按选定 Minecraft 版本的适配条件、用户需求和维护成本选择首个目标；不预先承诺全部支持。
- [ ] 识别天气／风况计算、观测语义、翻译和资源中可复用的部分，以及注册、事件、网络、持久化和渲染中需要分别适配的部分。先形成小范围方案，再确认是否需要共享模块或构建工具；不预先决定大规模重构。
- [ ] 首个目标完成构建与核心场景验证后，再评估其他组合。保留方块／物品 ID、服务端权威和数据版本保护；跨加载器切换世界必须单独验证，不能仅凭 ID 相同宣称兼容。

### 第三阶段：按组合记录支持与交付

- [ ] 为每个 Minecraft 版本 × 加载器组合分别记录“规划／开发中／已验证／已发布／停止维护”、精确源码提交、依赖、制品及测试边界。
- [ ] 安装说明和发布资产明确标注游戏版本、加载器与 Java 要求；一种组合的 JAR 或验收结果不能直接代表其他组合。
- [ ] 核心玩法和存档语义尽量保持一致，平台差异及缺失功能在对应说明中列明。专用服务端和多人实测仍须另获授权；未执行的项目保持未验证。

上述评估和移植均需另行确认具体任务范围，再走独立分支、验证和 PR。新增规划不改变当前安装要求，也不授权调整依赖、协议或实际功能。

## 1.x 以后：长期方向

以下均未作为独立系统实现，需先验证玩法价值和成本再定版本：

- 雾、阵雨、独立雪／暴雪天气；目前只有原版群系降雪表现。
- 温度与季节：现在湿度公式使用群系温度，不等于温度／季节系统。
- 区域天气、气团、天气锋面和长期演变；优先定义区域加载、边界、存档和网络预算。
- 稳定的只读天气／风况查询 API，待内部语义稳定后再公开支持契约。

每个实施任务仍走独立分支 → 验证 → PR → 维护者确认。路线方向可调整，存档安全、服务器边界和性能优先于扩种类。
